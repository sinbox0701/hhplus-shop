# 카프카(Kafka) 핵심 개념 학습 보고서

## 1. 카프카 개요

카프카는 LinkedIn에서 개발한 분산 이벤트 스트리밍 플랫폼으로, 대용량 실시간 데이터 파이프라인 구축에 사용됩니다. 높은 처리량, 낮은 지연 시간, 내결함성 등의 장점을 가지고 있어 현대 데이터 아키텍처에서 중요한 역할을 담당합니다.

## 2. 핵심 구성요소

### 2.1 Producer & Consumer

- **Producer**: 메시지를 카프카 브로커에 적재(발행)하는 서비스
- **Consumer**: 카프카 브로커에 적재된 메시지를 읽어오는(소비) 서비스
  - 메시지를 읽을 때마다 파티션별로 offset을 유지해 처리했던 메시지의 위치를 추적
  - CURRENT-OFFSET: 컨슈머가 어디까지 처리했는지를 나타내는 offset
  - 오류 발생 시 `--reset-offsets` 옵션을 통해 특정 시점으로 offset을 되돌릴 수 있음

### 2.2 Broker

- 카프카 서버 단위로, 메시지를 저장하고 관리
- Producer의 메시지를 받아 offset 지정 후 디스크에 저장
- Consumer의 파티션 Read 요청에 응답해 디스크의 메시지 전송
- **Controller**: 다른 브로커를 모니터링하고 장애가 발생한 Broker의 Leader 파티션을 재분배
- **Coordinator**: 컨슈머 그룹을 모니터링하고 리밸런싱(Rebalance) 관리

### 2.3 Message

- 카프카에서 취급하는 데이터의 단위로 <Key, Value> 형태로 구성
- 키는 메시지의 파티션 할당에 사용되며, 값은 실제 데이터

### 2.4 Topic & Partition

- **Topic**: 메시지를 분류하는 기준이며 N개의 Partition으로 구성
- **Partition**:
  - 토픽을 분할한 단위로, 메시지가 순차적으로 저장됨
  - 대용량 트래픽을 파티션 개수만큼 병렬로 처리 가능
  - 같은 파티션의 메시지에 대해서는 순차처리를 보장
  - 메시지의 키 해시를 활용해 저장될 파티션을 결정 (키가 없을 경우 Round-Robin 방식)

### 2.5 Consumer Group

- 하나의 토픽에 발행된 메시지를 여러 서비스가 소비하기 위한 그룹
- 보통 애플리케이션 단위로 Consumer Group을 생성, 관리
- 같은 토픽에 대한 소비주체를 늘리고 싶다면, 별도의 컨슈머 그룹을 생성하여 토픽을 구독

### 2.6 Rebalancing

- Consumer Group의 가용성과 확장성을 확보해주는 메커니즘
- 컨슈머 간 파티션 소유권을 재분배하는 과정
- 리밸런싱 발생 조건:
  1. Consumer Group 내에 새로운 Consumer 추가
  2. Consumer Group 내의 특정 Consumer 장애로 소비 중단
  3. Topic 내에 새로운 Partition 추가
- 리밸런싱 중에는 컨슈머가 메시지를 읽을 수 없음

### 2.7 Cluster

- 고가용성(HA)을 위해 여러 브로커를 묶어 구성
- Broker가 증가할수록 메시지 처리량을 분산시켜 확장성 확보

### 2.8 Replication

- Cluster의 가용성을 보장하는 개념
- 각 Partition의 복제본(Replica)을 만들어 백업 및 장애 극복
- **Leader Replica**: 각 파티션의 읽기/쓰기를 담당하는 주 복제본
- **Follower Replica**: 리더의 메시지를 복제하는 백업용 복제본, 리더 장애 시 새로운 리더로 선출될 수 있음

## 3. 카프카의 장단점

### 장점

1. **높은 처리량**: 대용량 데이터를 효율적으로 처리 가능
2. **확장성**: 브로커와 파티션 추가를 통한 수평적 확장 용이
3. **내구성**: 메시지 지속성 보장 및 데이터 손실 방지
4. **고가용성**: 복제를 통한 장애 대응
5. **순서 보장**: 파티션 내에서의 메시지 순서 보장
6. **분산 처리**: 파티션 기반 병렬 처리로 성능 향상

### 단점

1. **운영 복잡성**: 클러스터 설정과 관리가 복잡
2. **리소스 사용**: 많은 메모리와 디스크 공간 필요
3. **주키퍼 의존성**: 주키퍼 설정 및 관리 필요 (최신 버전에서 개선 중)
4. **모니터링 필요**: 지속적인 모니터링과 튜닝 필요

## 4. 사용 사례

1. **로그 수집**: 시스템 로그를 중앙 집중화하여 분석
2. **이벤트 소싱**: 이벤트 기반 아키텍처의 메시지 버스
3. **스트림 처리**: 실시간 데이터 스트림 처리
4. **비동기 통신**: 마이크로서비스 간 비동기 통신
5. **대용량 트래픽 처리**: 선착순 쿠폰 발급과 같은 대용량 트래픽 처리
